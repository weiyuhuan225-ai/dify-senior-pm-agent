# 架构与设计选择

## 三个应用的职责

主应用是 19 节点 Chatflow。需求指南和 PRD 成稿各是一个 3 节点 Workflow，作为主流程使用的工具。它们不依赖外部知识库或自建后端。

| 部分 | 负责 | 输出 |
| --- | --- | --- |
| 输入与控制分支 | 区分普通输入、命令和确认；核对当前修订 | 路由、规范状态或冻结快照 |
| 模型提取与原子合并 | 从本轮输入提出字段更新，校验后应用 | 更新后的需求状态与本轮变化 |
| 访谈 Agent | 根据允许字段选追问，解释方法，提出候选建议 | 经格式检查的回答或建议 |
| 只读需求指南 | 提供字段含义、完成标准与问题思路 | 方法指南，不是项目事实 |
| 规则与语义审查 | 检查结构与关联，提示缺口或冲突 | 十章摘要、覆盖关系、Review Notes |
| 确认与渲染 | 固定当前修订、确定性成稿、核对结果 | Markdown PRD 与状态更新 |

## 为什么同时使用 Workflow 和 Agent

下一轮该问什么、用户是否需要解释、怎样给出建议，存在对话上的不确定性，因此交给模型处理。状态如何合并、什么时候能成稿、输出哪些章节、修改后是否需要重新确认，使用固定程序规则。

Agent 的工具列表只有需求指南。它不能直接调用成稿工具；成稿节点由主 Chatflow 确认分支触发。这限制了模型对流程的控制范围，但并不保证模型始终正确理解用户语义。

## 会话状态

唯一会话变量 `session_json` 保存规范需求状态，包括 21 个字段、内容修订号、实体 ID、候选建议、审查结果与最近成稿。字段有待了解、待补充、待采纳、已记录、暂缓、不适用等状态。

模型返回的是变更提议。程序检查字段白名单、数据类型、证据文本、实体引用和操作，再整体合并；失败时不部分写入。本轮模型生成的候选建议与已记录需求分开保存。

实体使用 `G-`、`P-`、`US-`、`FR-`、`M-` 等编号；模型创建临时实体时使用 `tmp_` 标识，由程序统一分配持久编号。编号帮助维护关联，不证明关联在业务上正确。

## 修订、审查和成稿

需求内容发生变化时，内容修订号递增，旧审查和旧确认失效。审查保存该修订的内容哈希、覆盖关系与风险。用户通过包含当前修订号的命令确认；有待确认风险时，命令还需包含相应的接受说明。

成稿工具读取冻结快照，以固定十章模板渲染；主流程再对输出与预期结果进行比较。哈希用于一致性检查，不用于身份认证，也不是数字签名。主流程的确认门禁不应被外部服务直接调用成稿工具所替代。

## 十章 PRD

1. 概述
2. 目标与边界
3. 用户与权限
4. 用户故事
5. 功能需求
6. 用户体验
7. 使用叙事
8. 成功指标
9. 技术与风险
10. 建设顺序

缺失信息保留为待定，并进入审查说明。模板完整并不表示研究充分或需求通过专业验收。

## 源码与导出配置

`dify/` 是已有发布配置的公开副本；`src/` 是可维护实现。`build_dsl.py` 将 Python 规则和字段注册表嵌入 Dify Code 节点，从提示词与 Schema 构建其余节点。模板只保留构建必需形状；原工作区工具身份已替换为占位符。

这种嵌入方式不依赖外部 Python 服务，但会让多个 Code 节点重复携带运行时代码，增大 DSL。公开首版保留这一实现，便于按原流程复现。新的模型或 Dify 版本仍需要单独验证。
