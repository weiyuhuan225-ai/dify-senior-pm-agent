## 已复现的语义保护缺口

以下两项通过本地合成案例复现，首版保留原有运行逻辑。这些案例说明规则检查的范围，不能理解为正常对话中必然发生。

| 场景 | 复现条件与结果 | 使用时的影响 |
| --- | --- | --- |
| 否定采纳 | 用户输入“不同意 D-1”，而模型错误生成 `accept_proposal` 补丁时，当前正则会在“不同意”中匹配“同意”，因而可能采纳该建议。 | 程序不能保证排除所有否定采纳；需核对已更新内容和最终审查摘要。 |
| 否定范围丢失 | 用户输入“不自动发给客户”，而模型截取“自动发给客户”作为证据并写入肯定需求时，当前子串匹配会通过。 | 证据文本匹配不等于语义验证，不能保证完整保留否定范围。 |

模型负责解释输入并提出变更；程序主要验证格式、状态和引用。公开使用或继续开发时，应把上述情况纳入回归检查，并复核否定、歧义、数字及单位，避免把结构校验描述为事实正确性保证。

## 当前能力边界

- **输出格式：**当前成稿为 Markdown PRD 与 Review Notes。没有 Word 文件下载服务，也没有附件解析流程；Word 导出指令仅返回说明及已有 Markdown。
- **知识来源：**产品方法问答依赖所配置模型的知识，没有外部检索。涉及最新产品、市场或技术事实时，需要另外核验。
- **审查结果：**结构硬错误或未处理字段会阻断成稿。语义审查的 `FAIL`、`UNKNOWN` 会作为风险披露；字段状态满足条件且用户以精确口令接受待确认项后，仍可生成草案。语义审查不构成绝对质量门槛。
- **待定信息：**用户可以明确保留 TBD。字段已处理或章节完整不代表需求充分、指标已实测或方案可直接实施。
- **哈希用途：**内容哈希用于检查审查快照与成稿的一致性，不是数字签名，不提供身份认证，也不能作为防篡改安全边界。
- **测试范围：**31 项通过仅证明既有本地测试用例通过；尚未由本次工作验证真实模型的稳定性、并发性能、附件处理、跨工作区配置或在线服务状态。

## 使用前的最小检查

导入自己的 Dify 工作区并绑定工具与模型后，完成一次“说明想法 → 补充需求 → 审查 → 精确版本确认 → 生成 Markdown”的完整流程；再检查建议拒绝、否定句、需求修改后重新确认和模型输出异常等情况。对外使用前，人工核对成稿中的需求边界、指标依据与待定事项。
